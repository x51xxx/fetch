# Стеля чанка та `clone()`

Дві пов'язані теми, що лишились після Фази 1 стрімінгу
([`streaming-design.md`](./streaming-design.md)).

**Статус:** Частина 1 — досліджено, фікс не потрібен, поведінка зафіксована
регресійним тестом. Частина 2 — **реалізовано** (`test/clone.test.js`, 9 тестів).
Паритет буферизованого шляху з undici піднявся з 14/18 до **15/18**;
стрімінговий лишається 17/18, де `clone()` — свідоме відхилення.

---

## Частина 1. Чи може один чанк перевищити ліміт акцесора?

### Питання

`#consume()` в `index.js` перевіряє 32-мебібайтний бюджет **після** того, як
`nativeBody.read()` уже алокував і скопіював цілий чанк у Node:

```js
total += value.byteLength
if (total > BUFFERED_ACCESSOR_LIMIT) {
  /* відхилити */
}
```

Отже фактичний пік перевищує ліміт рівно на розмір останнього чанка. Питання:
чи може цей чанк бути великим — зокрема, чи може **декомпресія** роздути один
`Bytes` до довільного розміру (сценарій «zip-бомби»)?

### Механізм — з джерел

Декомпресія в цьому стеку йде через `tower-http`, і там є жорстка стеля:

```rust
// tower-http-0.6.11/src/compression_utils.rs:152
impl<M: DecorateAsyncRead> WrapBody<M> {
    const INTERNAL_BUF_CAPACITY: usize = 4096;
}
// ...
buf: BytesMut::with_capacity(Self::INTERNAL_BUF_CAPACITY),
```

`WrapBody` володіє власним `BytesMut` на 4096 байт і віддає декодеру **лише**
цю область; кожен кадр — це `split().freeze()` з неї. Декодер фізично не може
записати більше, ніж йому дали, тож коефіцієнт стиснення не впливає на розмір
окремого чанка — він впливає лише на **кількість** чанків.

### Вимірювання

Емпірично, не з міркувань:

| Сценарій                              | Чанків  | Найбільший чанк          | Приріст RSS |
| ------------------------------------- | ------- | ------------------------ | ----------- |
| gzip-бомба 1029:1 → 512 МіБ           | 131 072 | **4 096 Б**              | **11 МіБ**  |
| Звичайне тіло 512 МіБ (без стиснення) | 1 054   | **516 096 Б** (~504 КіБ) | пласко      |

### Вердикт: не проблема, фікс не потрібен

Перевищення обмежене приблизно **504 КіБ** — це **1.5 %** понад 32-мебібайтну
стелю. Для стиснених тіл (саме той сценарій, якого боявся дефект) воно ще
менше: 4 КіБ, тобто 0.012 %.

Контрінтуїтивна деталь, варта запам'ятовування: **стиснений шлях безпечніший
за нестиснений**. Декомпресія проходить через фіксований 4-кібібайтний буфер,
тоді як великі чанки приходять якраз зі звичайних тіл, де hyper склеює мережеві
читання.

Переносити перевірку в Rust (щоб відмовляти до копіювання в napi `Buffer`) не
варто: складність реальна, виграш — півмегабайта піку. Натомість зафіксовано
регресійним тестом, що бомба **не** підриває пам'ять і що `.text()` на ній
чесно відхиляється (`test/streaming-resources.test.js`).

> Окремо: не спокушатися «пресайзингом» з `Content-Length` у цьому шляху —
> у репозиторії є дочірньо-процесний тест, який доводить, що це кладе процес
> через SIGABRT. Див. `streaming-design.md`.

## Частина 2. Проєкт `clone()`

`clone()` — остання розбіжність із undici (`node test/undici-parity.mjs`:
стрім 17/18, буфер 14/18; промах в обох — саме `clone()`).

Два шляхи — дві **різні** задачі, і відповідь у них протилежна.

### 2.1 Буферизований `FetchResponse` — підтримати, майже безкоштовно

Тіло вже лежить `Vec<u8>` у Rust, а акцесори тут навмисно перечитувані. Тому
клон **не потребує копіювання даних узагалі** — достатньо нової JS-обгортки над
тим самим нативним об'єктом:

```js
clone() {
  const copy = new FetchResponse(this.#native)  // спільне нативне тіло
  return copy                                    // власний #bodyUsed, власні #headers
}
```

Вартість — один JS-об'єкт. Кожна обгортка веде свій `#bodyUsed` і свій
лінивий `Headers`, тож мутація заголовків клона не зачіпає оригінал.

**Чи має `clone()` кидати, коли `bodyUsed === true`?** За WHATWG — так. Тут —
**ні**, і це свідомо. На цьому шляху `bodyUsed` дорадчий, а `text()` можна
викликати двічі. Кидати на `clone()`, дозволяючи повторний `text()`, було б
суворішим правилом для слабшої операції — внутрішньо непослідовно. Це
відхилення належить до вже задокументованого «буферизовані тіла перечитувані».

### 2.2 Стрімінговий `StreamingFetchResponse` — **не підтримувати, кидати**

WHATWG визначає `clone()` через `tee()`. І саме тут це небезпечно **конкретно
для цієї бібліотеки**.

`ReadableStream.prototype.tee()` буферизує для повільнішої гілки **без
обмеження**. Споживач, який читає одну гілку й ігнорує другу, отримує рівно те
необмежене зростання пам'яті, заради усунення якого стрімінг і робився — при
виміряному виграші 206 МіБ проти 4.1 ГБ на тілі 2 ГіБ. `clone()` виглядав би
дешевим викликом, а коштував би розміру всього тіла.

Додаткові проблеми, кожна з яких сама по собі неприємна:

- **Бекпрешер ламається.** Джерело навмисно має `{ highWaterMark: 0 }`, щоб
  `pull()` означав справжнє споживання. `tee()` читає з нижчого стріму зі
  швидкістю **швидшої** гілки, тож ліниве джерело перестає бути ліниве, і
  бекпрешер до TCP-вікна більше не доходить.
- **`maxResponseBytes` рахується один раз.** Лічильник живе в Rust і спільний
  для всього, що читає тіло. Дві гілки, що споживають один нативний стрім, —
  один лічильник; «на гілку» він не поділиться без переробки.
- **Семантика `cancel()` нетривіальна.** За WHATWG скасування однієї гілки не
  скасовує підлеглий стрім, доки не скасовані обидві. Тобто `cancel()` на
  клоні мовчки нічого не звільняє — знову протилежно до обіцянки API.

**Рекомендація: кидати виразну помилку і вказати на `tee()`.**

```js
clone() {
  throw new TypeError(
    'clone() is not supported on a streamed response: teeing a stream buffers ' +
    'the slower branch without bound, which defeats the point of `stream: true`. ' +
    'Use `response.body.tee()` explicitly if you accept that cost.'
  )
}
```

Обґрунтування: примітив **уже є** і він самодокументований. Хто справді
потребує двох споживачів, викличе `res.body.tee()` — і вартість тоді видимо
його, а не схована за нешкідливим на вигляд `clone()`. Чесна задокументована
відмова краща за пастку.

Чого **не** робити:

- Не реалізовувати «`clone()` з обмеженим буфером, що кидає при відставанні» —
  це третя семантика, якої немає ні в WHATWG, ні в undici, і вона падала б
  недетерміновано, залежно від того, як швидко читає споживач.
- Не буферизувати тіло тихо, щоб `clone()` «просто працював» — це мовчазне
  скасування `stream: true`.

### 2.3 Що покрити тестами

| Тест                                                | Що доводить                                |
| --------------------------------------------------- | ------------------------------------------ |
| Буферизований `clone()` віддає той самий вміст обом | Спільне нативне тіло читається двічі       |
| `bodyUsed` незалежний в оригіналі й клоні           | Обгортки не ділять стан                    |
| `Headers` клона незалежні                           | Мутація одного не тече в інший             |
| `clone()` після читання оригіналу працює            | Узгоджено з перечитуваністю шляху          |
| Клон клона                                          | Немає накопичення стану                    |
| Стрімінговий `clone()` кидає `TypeError`            | І повідомлення згадує `tee()`              |
| `res.body.tee()` і далі працює                      | Відмова стосується `clone()`, не примітива |

### 2.4 Вплив на паритет

Реалізація підніме буферизований шлях з 14/18 до 15/18. Стрімінговий лишиться
17/18 — і це правильна цифра: розбіжність тут **свідома**, і місце їй у
таблиці відхилень `docs/fetch-compatibility.md`, а не у списку багів.
